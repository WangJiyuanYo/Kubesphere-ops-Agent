| 问题 | 原行为及影响 | 当前处理 | 证据 |

| 启动校验晚于调度器初始化 | 原校验放在 ApplicationRunner，不能保证调度开始前完成；零时限也未拒绝 | 将校验移动到配置绑定阶段，拒绝非法真实环境配置、零时限及过短租约 | AgentPropertiesTest 的五项绑定测试 |

## 上线自动模式前优先补充

### 1. 平台原子受理与目标归属契约

位置：KubernetesDeploymentPort.retry、RunController.create。

当前注册请求由调用方同时提供 provisioningId 与目标 CR，但 Agent 不能从平台现有详情 DTO 验证两者完整对应。恢复接口只接收 requestKey，也无法原子验证 Agent 观察的 UID、generation、版本和配置摘要。采证完成后，平台可能已经切换到另一版本。

建议由平台提供受权的目标快照查询，注册时冻结目标归属和发布版本；恢复受理时在平台同一事务 / 发布锁下核验 expectedVersion、目标快照摘要及 requestKey，不符合时返回稳定冲突。Agent 收到冲突必须终止旧方案。这个缺口涉及配套平台契约，本次未跨仓修改；在补齐前应使用显式目标、发布互斥和批准模式进行试点。

### 2. 证据完整性与故障分类

位置：KubernetesDeploymentPort.collectRelated、RecoveryPolicy.classify。

目前一个容器日志接口出错会中断整次采证，已有 CR 故障证据也不会提交；Helm 资源缺少 ownerReference 时日志无法覆盖。分类使用一段聚合文本，历史日志里的 503 或普通数字 503 可能参与重试判定。

建议增加带资源身份、采集时间、来源和错误类型的结构化证据；保留已成功采集的 CR 证据，把可选日志读取失败记录为缺口，证据不足时输出受限方案且禁止自动动作。优先按当前 CR / Pod 的结构化故障原因与同时间事件选择 runbook，文本仅作为佐证。Helm 日志需复用受审的 release 与所有权映射，不能扩大为任意命名空间日志。

### 3. 调度并发、采证总超时与租约续期

位置：RunScheduler.tick、RunEngine.step、KubernetesDeploymentPort.observe。

每实例每 5 秒串行认领一个任务，慢采证或模型请求会阻塞其他任务。N 个持续到期任务再次获得检查的间隔约为 N ×（调度间隔 + 单步耗时），并非每个任务每 5 秒采样。20 个验证任务可能仅排队就耗尽 5 分钟窗口。多个目标和容器的单请求超时还可能累计超过执行租约。

建议按可用工作线程槽位认领任务，采用有界线程池和并发上限，认领后立即执行；每个任务设置独立采证总预算，长计算期间续租，失去租约后停止后续外部动作。压测需覆盖慢模型、慢 API 与多任务，并确认不会因队列延迟误报部署故障。不能通过无界批量认领或单纯调大时限代替调度治理。

### 4. 与任务绑定的应用验收

位置：AgentProperties.verificationUrl、KubernetesDeploymentPort.verify。

当前每个进程固定一个健康地址，适用于同一部署域。若一个进程监控不同项目或服务，固定地址可能探测到另一个正常应用。

建议按部署任务绑定后端受权的 verificationProfile，服务端目录映射目标入口和预期版本；验收至少包括路由、应用版本和关键依赖的只读连通性。不得直接接受客户端任意 URL。数据恢复和有副作用的业务验收需另定义权限与补偿，不能把所有检查都归结为 Pod Ready 或单个 UP。

## 后续能力补充

| 优先级 | 能力 | 当前缺口与建议 |
| --- | --- | --- |
| 高 | 自动接入部署任务 | 当前必须注册已有 CR，开通前置失败或 CR 尚未创建时无法覆盖。增加平台发布事件 / Webhook 或持久化任务扫描，先绑定平台版本，再随阶段发现 CR；重复事件按同一故障周期去重，避免新任务不断续发预算 |

| 高 | 人工处理与失败通知 | 当前结果需主动查询。增加持久化通知事件、投递重试与去重，通知人工接管、预算耗尽和最终结果；本次未向任何外部系统发送通知 |
| 中 | 运行观测与审计 | 增加任务列表、阶段延迟、队列等待、模型耗时与费用、自动恢复成功率、不可变动作审计和历史保留策略 |
| 中 | 持续集成与故障演练 | 默认无 TEST_DATABASE_URL 时会跳过数据库测试。CI 应提供专用 PostgreSQL，加入进程崩溃、响应丢失、双实例接管、API 403/429 和模型超时演练，再做指定非生产集群联调 |
| 按需要 | 完整流程 Graph | 当前 Graph 编排诊断，业务状态机负责持久化副作用。若需要整条流程的图可视化和节点级暂停恢复，可扩展为观察、诊断、策略、批准、执行和验证节点；应保留单一权威执行账本，避免同时维护 Graph Checkpointer 与另一份独立状态机导致双重推进 |

## 推荐实施顺序

1. 先联调平台原子目标契约、结构化证据与准确应用验收。
2. 补充有界并发、采证总预算和租约续期，再进行并发压测。
3. 接入部署事件和通知，使任务自动进入与退出流程。
4. 扩展少量有验证和补偿定义的排障手册；按产品可视化需要决定完整 Graph 改造。

以上推荐顺序记录评审时的设计依据，具体交付状态见文首；当前规则已同步 README 和 PRD，尚未现场验证的边界不计入已验证能力。
